## Validation addendum for newly requested fixes

The user added DJI LRF, filesystem capture dates, and copy-first/validate-after requirements during this audit. These changes are implemented in source; the installed production app has not been replaced or restarted.

- DJI LRF regression was observed failing before inclusion and pairing fixes, then passing. Both standalone and paired LRF preserve original bytes/names; a pair shares routing without making subtitles/metadata ambiguous. Proxy video remains visible in format summaries. See [LRF research and ChatGPT consultation](dji-lrf.md).
- macOS Created and Modified use recorded capture time. Backups or absent/invalid capture metadata preserve original filesystem timestamps. Dates are set on exclusively owned descriptors; APFS avoids native helper processes when descriptor utimes already produces both dates. Plans and signed organization journals persist the capture instant for recovery. Windows/Linux Modified is supported, but creation-date mutation remains unsupported. Finder displays stored instants in the Mac's timezone; explicit capture offsets are respected. Existing duplicate files are not retroactively retimestamped.
- Ordinary imports stage all pending files for one transfer/destination before standalone validation readbacks. They keep original contents unchanged, with no media decoding/re-encoding. Transfer writes use 1 MiB blocks; copying through blocks does not change file fidelity. Preflight hashes/destination duplicate checks and SHA accumulation from already-read buffers remain. Phases are per transfer, so independent concurrent jobs may be in different phases.
